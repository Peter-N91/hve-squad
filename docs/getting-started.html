Consumer Guide

Getting Started

Install hve-squad in your Copilot environment, select the coordinator, and run your first request.

1. Install for your environment

All hosts and platforms: install PowerShell 7+ (pwsh). The Squad Scribe writes the cost ledger and runs its end-of-turn self-check with Measure-SquadLedger.ps1, and routing=ranked|manual resolves models with Resolve-SquadModelRoute.ps1. Both require PowerShell 7 or later — Windows PowerShell 5.1 is not enough. Without pwsh the squad still runs, but falls back to deriving the ledger by hand, which is slower, uses more tokens and is less reliable. The optional Azure scaffold scripts require it outright. The plugin hooks do not need it: they ship bash equivalents.

Windows: winget install --id Microsoft.PowerShell -e · macOS: brew install --cask powershell · Linux: follow Installing PowerShell. Check with pwsh --version, then restart your Copilot client so it finds pwsh on PATH.

Copilot CLI

Install GitHub Copilot CLI, sign in with an account that has Copilot access, and open a terminal in your own project repository. Install both marketplace entries:

copilot plugin marketplace add Peter-N91/hve-squad-plugin
copilot plugin install hve-squad@hve-squad-plugin
copilot plugin install hve-squad-hve-core@hve-squad-plugin
copilot

In the agent picker, Squad Coordinator may be displayed as hve-squad:squad-coordinator. Continue with initialization below after checking the installation.

Check agent availability

Ask the coordinator to run squad-doctor before dispatching work. The plugin distribution can lack HVE Core domains. If the report identifies missing domains, use the documented full-package remedy in your repository:

apm install github/microsoft/hve-core --target copilot

Do not install the official hve-core plugin alongside hve-squad-hve-core. For updates, reinstall the companion entry rather than using plugin update on it. Follow the CLI installation and update guide.

Copilot App

Open your project in the GitHub Copilot desktop app and sign in with Copilot access. In the app's plugin settings, register Peter-N91/hve-squad-plugin and install both hve-squad and hve-squad-hve-core. Names and settings locations can vary by app version; follow the desktop installation guide.

Verify the pair is installed in the app itself. A terminal installation may use a different COPILOT_HOME and does not prove the app has the same plugins.

Look for the Squad Coordinator agent, possibly listed as hve-squad:squad-coordinator, not a similarly named skill. Ask for squad-doctor and resolve missing agents before work starts; the plugin documentation records current domain gaps and the full APM package remedy.

Do not add a second, official hve-core plugin alongside the companion. Update both entries in the app's plugin home, reinstalling hve-squad-hve-core when its pin changes.

VS Code

Open your project in VS Code with GitHub Copilot Chat enabled and authenticated. Choose either the plugin installation or the repository package route below.

Option 1 — Install the plugins in VS Code settings

In VS Code, open Settings → Extensions → Copilot → Plugins, register Peter-N91/hve-squad-plugin, and install both hve-squad and hve-squad-hve-core. Names and settings locations can vary by VS Code version; follow the VS Code installation guide.

Verify the pair in VS Code itself before the agent picker and initialization below. A terminal installation may use a different COPILOT_HOME and does not prove Copilot Chat has the same plugins. In the agent picker, Squad Coordinator may be displayed as hve-squad:squad-coordinator.

Do not install the official hve-core plugin alongside hve-squad-hve-core. For updates, reinstall the companion entry rather than using plugin update on it, as the VS Code installation guide describes.

Option 2 — Install the package into the repository with APM

This route installs the full cast into the repository through APM.

Prerequisites

  • PowerShell 7+ (pwsh) on every platform — see the note above; on macOS and Linux the APM commands below run in your usual zsh/bash shell
  • Git
  • APM CLI 0.29.0 installed and available in PATH
  • Access to the microsoft/hve-core repository
  • Authenticated GitHub access (gh auth login or GITHUB_TOKEN) — strongly recommended; see the note in step 1

APM CLI 0.29.0 is required for the APM installation path. APM 0.29.0 is the latest version known to install all HVE Squad dependencies successfully. A regression in 0.29.1 and 0.30.0, which an unversioned installer may select, causes the same 11 dependencies to fail. The APM CLI version and the HVE Squad package version are separate pins: apm --version must report 0.29.0, while #vX.Y.z selects the HVE Squad release.

Install APM CLI 0.29.0

Windows (PowerShell)

$env:VERSION = 'v0.29.0'; irm https://aka.ms/apm-windows | iex
apm --version  # must report 0.29.0

If the version is still wrong, open a new PowerShell window and check again. Use Get-Command apm -All to find an older executable that appears earlier in PATH.

macOS (Apple Silicon or Intel)

# Run this only if Homebrew currently manages apm; the pinned installer cannot overwrite it.
brew uninstall apm

curl -sSL https://aka.ms/apm-unix | sh -s -- @v0.29.0

# The installer uses ~/.local/bin. Add this line to ~/.zshrc to persist it.
export PATH="$HOME/.local/bin:$PATH"
hash -r
apm --version  # must report 0.29.0

If you prefer an isolated installation rather than changing the Homebrew-managed copy, install the same version with uv tool install apm-cli@0.29.0. Resolve any PATH ambiguity before continuing.

Install the package

Run apm install from the root of the project you want the squad in.

Replace vX.Y.z in the examples with a published tag from Releases.

Heads-up (APM 0.18.0+). APM no longer silently defaults to the Copilot harness. In a project with no existing .github/agents/, .github/prompts/, .github/instructions/, .claude/, .cursor/, etc., apm install fails with [x] No harness detected after downloading sources into apm_modules/ but before deploying anything into .github/. Tell APM which harness to deploy to using one of the options below.

Authenticate first — it makes the install fast. This package pulls hundreds of files from microsoft/hve-core. Unauthenticated GitHub access is rate limited to 60 requests/hour, which can stretch a first install to 30+ minutes — APM waits on the rate-limit reset rather than failing, so it looks stuck. Run gh auth login (APM detects it automatically) or set GITHUB_TOKEN before installing to get 5,000 requests/hour. hve-core is public, so a token with basic read scope is enough. See Troubleshooting if an install is already crawling.

Option A — pass --target copilot on every install (one-off)

apm install "Peter-N91/hve-squad#vX.Y.z" --target copilot  # pinned (recommended)
# or
apm install Peter-N91/hve-squad --target copilot           # latest on default branch

Option B — declare the target once in your project's apm.yml (persistent, recommended)

Create an apm.yml at the root of your consumer project:

name: my-project
version: 0.1.0
targets:
  - copilot

Then apm install "Peter-N91/hve-squad#vX.Y.z" (no flag needed) deploys to Copilot from now on. This also makes future apm install / apm update runs reproducible.

Either way, this deploys the bundled HVE Core agents, prompts, instructions, and skills — plus the squad — into your project's .github/ tree. Consumers do not need sync-deps or install-sync; those are maintainer-only scripts.

If your first install already failed with No harness detected: the sources are already in apm_modules/. Re-run with --target copilot (Option A) or add the targets: block to apm.yml (Option B) and re-run apm install; APM re-runs the deploy step and populates .github/.

Re-deploy after an update

Re-run install with the published tag you want, including --target copilot unless your project declares targets::

apm install "Peter-N91/hve-squad#vX.Y.z" --target copilot

To test merged work before release, follow Install and test the pre-release for the current tag and exact command. That tag moves; pin a stable release for work you depend on. Reinstallation refreshes .github/, not your state under .copilot-tracking/squad/.

2. New here? Chat with the Squad Coach

Once HVE Squad is installed, the Squad Coach works before initialization: neither team.md nor federation.md has to exist. Describe the outcome you want without choosing a profile, pack, or autonomy mode first. The Coach reads the code, entrypoint contracts, and documentation shipped in your installed version, plus any state that already exists. It discovers the workflow for your demand rather than following a fixed feature checklist, then advises you without creating or changing anything.

In VS Code, select Squad Coach from the Copilot Chat agents dropdown. In Copilot CLI, enter /agent and choose Squad Coach. In Copilot App, select Squad Coach. The plugin may display it as hve-squad:squad-coach. All three hosts use prefix-free messages in the selected agent's conversation; the tabs below name the agent and show what to send. 

/squad-coach request="I need to modernize two applications owned by different teams. Help me choose the simplest setup and prepare my first prompt."

Advice only. The Coach does not initialize a squad, dispatch delivery work, change configuration, or migrate state. It gives you a copy-ready handoff for the Squad Coordinator or Federation Coordinator, which you invoke explicitly when you are ready.

What the Coach asks and returns

The Coach asks only questions that can change the recommendation: your goal and success criteria, project and scope, required deliverables, owners and dependencies, constraints, environment, access categories, and approval expectations. It never asks you to paste a secret.

A complete recommendation includes:

  • a justified single-squad or federation choice, including when to reconsider it;
  • supported profiles and capability packs, per federation member when needed, explained in plain language;
  • essential and optional inputs, with a safe way forward for missing information;
  • exact commands and prompts tailored to your installed version and host; and
  • a detailed, ordered runbook from your current stage to the requested outcome, naming the agent or terminal for each step, expected outputs, approval checkpoints, source citations, and how to resume.

Single squad or federation?

ChooseWhen it is sufficientTrade-off and later change
Single squad (default) One shared outcome, delivery lifecycle, ownership boundary, and set of artifacts. Add a supported pack when the work needs a technology specialty. Least setup and coordination overhead. Complexity or many roles alone is not a federation reason.
Federation Two or more durable workstreams need independent owners, scopes, deliverables, routing, constraints, access boundaries, or cadence. Independent state and routing, but duplicated rosters and more coordination. Each member needs its own profile and any packs.
Promote later An existing single squad gains a genuinely independent team or workstream. Ask the Coach to re-evaluate, then use the current promotion flow so the coordinator preserves existing state and artifacts: 
/squad-federation promote

Preparation checklist

Essential inputs — prepare what determines the work and its safe boundaries:

  • goal, audience, scope, required deliverables, and success or acceptance criteria;
  • repository or project context, hard constraints, known dependencies, and ownership;
  • environment prerequisites and the categories of access that will be required.

Optional inputs — useful when available, but not a reason to block a safe first conversation:

  • requirements, relevant documents, current architecture, backlog, examples, and test evidence;
  • timelines, stakeholder preferences, detailed environment information, and non-blocking assumptions.

If an essential answer can change topology or safety, the Coach asks before recommending. It labels non-blocking gaps as assumptions and tells you whether the coordinator can discover, defer, or validate them. Never paste tokens, passwords, private keys, connection strings, or credential values. State only that an access category is available and configure its value through the host's secure secret mechanism later.

The Coach reads the selected installed version; it does not install or update releases. Update your installation first when you want a newer contract. It re-reads affected sources when the version or project state changes, but cannot guarantee every future undocumented change.

Beginner example conversations

One shared application

User: “We have one Node application and want a tested plan for adding login validation. One team owns it.”

Coach: “Start with one default squad. The outcome, owner, plan, implementation, and review are shared, so a federation would add overhead without isolating anything. Prepare the repository, acceptance criteria, supported Node version, and test command. If security review becomes the primary outcome, we can re-evaluate the profile.”

Independent product and platform work

User: “A product team owns requirements and launch material. A platform team independently owns the Azure landing zone, with separate approvals and release dates.”

Coach: “Use a federation with a product member and an azure member. Their owners, deliverables, access, approvals, and cadence are independent; federation routing keeps those histories separate. Record their dependency—approved requirements before platform sizing—and initialize only after confirming both member proposals.”

An A-to-Z runbook example

For one application owned by one team, the Coach can produce the following path. These are current examples, not instructions baked into the Coach: it reads your installed contracts and replaces the profile, settings, and steps to match your demand. Skip already-completed setup. Shell commands belong in your project terminal; the blocks below are chat messages for the agent named by the selected host tab.

  1. Prepare and check the installation. Follow the installation panel above in the project repository. Confirm the required agents are available, prepare acceptance criteria and the project's test command, then ask the Coach for any missing prerequisites. Coaching itself creates no state.

  2. Initialize interactively and choose ranked models. Select Squad Coordinator and send:

    /squad init profile=default routing=ranked

    Confirm the proposed topology, profile, roles, member naming, and approval channel. Only then does the Scribe create the squad state. Inspect .copilot-tracking/squad/team.md: Model routing: ranked and its Model column show the selected models. Ranking chooses among models your host supports; it does not change the coordinator's session model. See Model selection per role.

  3. Prepare the first cost-controlled run. Initialization seeds consumption-rates.md with observations: 0 and last_reconciled: never. A positive ceiling therefore produces cannot-confirm, which approval cannot waive. Ask the Coordinator to plan preparation, not to start an uncapped run:

    /squad request="Explain Cost Preflight prerequisites and propose a small calibration run; wait for my explicit approval before any uncapped dispatch"

    If you approve that separate uncapped preparation, collect real per-user ai_credits_used measurements before and after the small run, isolate its usage window, and have the coordinator arrange the Scribe's reconciliation against the run's estimated credits. Verify positive observations, a non-never reconciliation date, and calibration_basis matching the current Observed-on and estimator_revision. Never invent measurements. If access is unavailable or you decline uncapped preparation, remain blocked on capped work. See Before the first capped run; a larger ceiling does not repair missing evidence.

  4. Run the requested work in autopilot. Only after the preceding preparation verifies eligible calibration and the other Cost Preflight prerequisites, send a separate work request in the same Coordinator conversation:

    /squad request="Add input validation to the login form, with tests for valid and invalid inputs" mode=autopilot cost-ceiling=10

    The persisted ranked policy is reused. Autopilot sequences research, plan, implementation, and review; it does not approve impactful actions or the final outcome for you. The example ceiling is an estimated model-spend control, not a bill guarantee; choose your own positive value. Running without this protection is a separate, explicit choice, not a remedy for a blocked capped request. Expect the requested changes, tests, and review evidence. See Cost admission control.

  5. Inspect, approve, and continue. Read the progress and final summary, inspect the deliverables and review evidence, and run your project's tests. Answer required human gates in the configured approval channel. To resume rather than initialize again, send:

    /squad request="Summarize this run, show any blocked approval, and continue from the last completed stage"

    The coordinator uses existing state and identifies the safe next step. Return to the Coach whenever you need an explanation or a revised runbook.

  6. Only if ownership later splits: plan a federation promotion. Ask the Coach to justify the split and prepare member profiles, owners, and dependencies. Select Squad Federation Coordinator and send:

    /squad-federation request="Promote the existing squad and propose a separately owned platform workstream" promote

    Review and confirm the proposal before migration. Promotion adopts the existing squad and preserves its state and artifacts; it is not a fresh initialization. Check the registry in .copilot-tracking/squad/federation.md. Do not promote merely because a task is complex.

  7. Continue through the federation. Use the confirmed member name from that registry, replacing the placeholder below:

    /squad-federation request="Continue the platform work from its last completed stage" squad=<confirmed-member> mode=autopilot

    A targeted request runs that member's pipeline. An untargeted federation autopilot request coordinates multiple selected members and uses aggregate cost admission. Ask the Coach for the correct path and approvals for your goal; see Federation.

Install and test the pre-release

These docs follow main, which can be ahead of the latest stable release. A Pre-release only badge identifies a feature that has merged but has not shipped in a stable release. Guide authors attach each pending change fragment to the smallest affected feature label, paragraph, list item, heading, table cell, or code block. The site renders a badge only for those explicit markers; an official release consumes the fragments and removes the badges automatically. The notice on every page shows both versions, and each badge links here. Use stable releases for work you depend on.

Test in a separate scratch repository with PowerShell 7+ and APM CLI 0.29.0; confirm with apm --version. The published site fills in the current command below. You can also find the tag marked as a pre-release on Releases.

  1. Install the full APM package in the scratch repository. The plugin and MCP mirrors follow stable releases; installing or updating those does not install this pre-release. Do not mix the stable plugins and the APM preview in the same test environment.
  2. Restart your Copilot client, select Squad Coordinator, send init, and confirm the proposed team.
  3. Send a small request exercising the badged feature and inspect the resulting artifacts. Report unexpected behavior with the pre-release tag, the resolved commit in apm.lock.yaml, reproduction steps, and expected versus actual results; remove private project data before sharing.

The rolling tag moves on every merge. Re-run the install to refresh it, and check the notice again because a higher release bump can rename the tag. Use the command below to return to stable; reinstallation does not reset your local squad state, so keep preview testing isolated.

3. Initialize the squad

The squad is a user-invocable Squad Coordinator that routes your request to a cast of HVE Core agents and persists its state under .copilot-tracking/squad/. Initialize and confirm the proposed team first: 

/squad init

4. Send a work request

After confirmation, send a separate work request. Use mode=autopilot to sequence the work while keeping required human approvals, or omit it to approve each step:

/squad request="add input validation to the login form" mode=autopilot

In VS Code Copilot Harness, open the agents dropdown and select Squad Coordinator before sending each request. Send the request text shown above without the /squad prefix. The @squad.prompt.md route remains available, but it adds intermediary agent calls and is slower.

On a fresh project the coordinator inspects your repo and proposes a profile before creating anything. See Usage for profiles, autonomy modes, and remote approval.

Optional: set a model-spend ceiling

Add cost-ceiling=<positive USD> when you want the squad to forecast the remaining work before dispatching it. The ceiling governs estimated model spend for the current run; it is not a GitHub invoice guarantee and does not govern Azure workload cost. Complete the first-ceiling preparation before using the example: freshly seeded pricing files are not calibrated, so the first capped work request remains blocked as cannot-confirm until real, eligible reconciliation exists. 

/squad request="add input validation to the login form" cost-ceiling=10

If the forecast is above the ceiling, the squad shows the estimate and lets you stop or proceed in bounded sequential units. It starts no new unit after accumulated estimated spend reaches the ceiling. On a fresh project, confirmed initialization runs outside the ceiling so the Scribe can create the state and pricing files; the ceiling applies before the original request starts work. Omit the argument on later requests to inherit the ceiling within the same run, or use cost-ceiling=unset to remove it. See Usage → Cost admission control for the full lifecycle and examples.

Optional: scaffold the Azure execution layer

If you seed the azure profile, the squad can scaffold an Azure build-and-deploy toolchain into your repo — a dev container, azure/login@v2 OIDC deploy workflows for Bicep and Terraform, a one-time OIDC setup script, a governance policy baseline, and the infra/ folder convention. Ask the coordinator to scaffold it, then review and commit the copied files. Deploys always run behind the Impactful-Action Gate, so nothing reaches Azure without your approval.

  • An Azure subscription (Owner or User Access Administrator to run the one-time OIDC setup).
  • The Azure CLI (az) and GitHub CLI (gh) — both provided by the bundled dev container.

See Usage → Azure execution layer for the full scaffolding flow.
