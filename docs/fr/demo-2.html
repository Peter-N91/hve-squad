Démonstration 02

Migration autopilot

Une demande produit un dossier de migration. La revue trouve des blocages et s'arrête : ce scénario montre une escalade, pas un déploiement réussi.

Toutes les démonstrations · Azure · Produit · .NET

Contexte et préparation

Le parcours d'origine utilise le dépôt préparé hve-squad-demo2, des définitions de processus Contoso et des documents privés dans knowledge-docs/. Ces documents ne sont pas distribués avec ce site. Pour le reproduire, utilisez votre propre contexte autorisé et le profil azure.

Le périmètre porte sur l'étude et les fichiers de préparation, sans déploiement Azure. Vérifiez les agents disponibles et, pour les diagrammes avec icônes, Python ou uv et Graphviz. Mermaid reste possible sans ce rendu.

Un dossier ignoré par Git ne suffit pas à empêcher une fuite. Les documents privés sont un contexte de lecture ; examinez aussi les livrables et le diff pour vérifier qu'aucune donnée confidentielle n'a été reproduite.

La demande

Initialisez et confirmez d'abord l'équipe, puis envoyez la demande :

/squad profile=azure mode=autopilot request="Planifie et prépare la migration de ce projet depuis l'environnement local vers Azure.

Contexte : lis les définitions de processus du dépôt et ./knowledge-docs pour comprendre le besoin.

Livrables : architecture cible justifiée, plan de migration concret, IaC sous infra/, estimation des coûts, revue de sécurité, HLD Mermaid et LLD avec icônes si l'outillage est disponible.

Contraintes : ./knowledge-docs est privé. Ne reproduis pas son contenu dans les fichiers suivis, livrables ou sorties à publier. Aucun déploiement. Arrête-toi sur les blocages et attends ma décision."

Résultats du parcours d'origine

Ces observations décrivent le run documenté, pas une garantie de résultats identiques dans votre projet :

RechercheÉtude de faisabilité et correspondance des services pour un contexte de 117 clients.Terminée

L'architecture proposée associait Azure Container Instances et PostgreSQL managé dans une organisation hub-spoke. La prévision historique était d'environ 598 000 à 648 000 USD la première année et 2,4 millions USD sur trois ans. Ces chiffres ne sont ni une tarification actuelle ni une estimation pour votre projet.

Les cinq blocages de la revue

ConstatConséquence
Erreurs de compilation BicepPortées, fonctions ou schémas incorrects : déploiement impossible.
Chemins CI/CD incohérentsDes workflows pointent vers des fichiers absents.
Validation de déploiement contournéeUn accord à deux personnes est documenté mais l'implémentation approuve automatiquement.
Tests d'intégration non mesurablesLes cinq scénarios attendent un déploiement réel ; leur succès n'est pas démontré.
Supervision incomplèteCinq alertes implémentées pour quatorze annoncées.

La décision humaine

La squad a proposé soit une remédiation avec responsables puis nouvelle revue, soit une synthèse d'escalade et l'arrêt. L'utilisateur a choisi l'escalade : aucune correction n'a été appliquée dans ce run et aucune validation finale n'a été obtenue.

La reprise prévue attribuait les erreurs Bicep à l'auteur IaC, les chemins CI/CD au Deployer, les tests au développeur, la supervision au rôle concerné et la revalidation au tester. Les estimations d'effort du parcours d'origine ne constituent pas un engagement pour une nouvelle exécution.

Présenter honnêtement le résultat

  • Montrez les fichiers générés et leurs limites, pas seulement le résumé du coordinateur.
  • Si l'IaC ne compile pas, présentez le rapport de revue et l'escalade ; ne forcez pas un déploiement.
  • Si un agent ou un outil manque, consignez le blocage avant d'adapter l'équipe.
  • Ne présentez pas le contrôle de qualité comme une garantie absolue de détection.
