Démonstration 04

Modernisation .NET

Faire évoluer une solution existante, garder une décision humaine sur les risques et vérifier les corrections avant la validation finale.

Toutes les démonstrations · Azure · Migration · Produit

Contexte

Le run documenté porte sur hve-squad-modernize-dotnet, une application de gestion de stock volontairement ancienne : bibliothèque, console et 20 tests MSTest sous .NET Framework 4.8. La cible de ce scénario est .NET 10. Il s'agit d'une mise à niveau sur place, pas d'une nouvelle application.

Préparez le dépôt, hve-squad, la capacité de délégation et le SDK .NET 10. Contrôlez dotnet --version. Sans SDK approprié, l'analyse reste possible mais vous ne pouvez pas revendiquer des builds ou tests exécutés. Aucun déploiement cloud n'est nécessaire ; la consommation Copilot reste distincte.

La demande

Confirmez d'abord l'équipe et les spécialistes requis, puis envoyez la demande :

/squad mode=autopilot request="Modernise ce dépôt de .NET Framework 4.8 vers .NET 10. Évalue les projets et dépendances, définis la cible puis réalise la mise à niveau sur place. Préserve le comportement, rends explicites les risques et vérifie les builds et tests. Attends mes décisions aux validations requises."

Les résultats ci-dessous sont ceux du parcours d'origine, pas des mesures réalisées par cette documentation.

Première escalade

Le chercheur a signalé un outillage de délégation manquant et suspendu le travail. L'utilisateur a approuvé une réaffectation au Squad Modernization Planner. La décision a été conservée au lieu d'être masquée par une substitution silencieuse.

Analyse et contrôle des risques

L'analyse a identifié les projets non SDK, MSTest v1 lié au GAC, la configuration spécifique au framework et les builds dépendant des chemins Visual Studio. Le conseil a rendu un accord conditionnel :

DomaineConditions
ArchitectureDocumenter le changement de plateforme de tests, stabiliser le contrat de build et expliciter la stratégie de configuration.
SécuritéRisque élevé : ajouter SAST et SCA ainsi qu'une politique de confiance des dépendances avant fusion.
IA responsablePérimètre non matériel pour cette migration ; conserver les revues et la traçabilité.

Le risque élevé a déclenché une décision humaine. L'utilisateur a autorisé la poursuite sous conditions dans le mode consultatif du scénario. Cette décision ne constitue pas une règle permettant de contourner les contrôles sur un autre projet.

Changements réalisés dans le run d'origine

AvantAprès
Projets historiques .NET Framework 4.8Projets SDK ciblant net10.0.
MSTest v1 via le GACMicrosoft.NET.Test.Sdk, MSTest.TestFramework et MSTest.TestAdapter via NuGet.
Build dépendant de Visual StudioCLI dotnet et SDK épinglé dans global.json.
Anciennes métadonnées de configurationNettoyage de la configuration obsolète.
Absence de CI et de scansWorkflows de build, tests, SAST et SCA.

La validation rapportait une restauration réussie, des builds Debug et Release et 20 tests sur 20 réussis. Le renforcement des analyseurs et de la nullabilité était reporté explicitement, pas déclaré terminé.

Revue, corrections et nouvelle revue

La première revue a détecté trois écarts malgré le build réussi :

  1. Le job CodeQL pouvait utiliser un autre SDK que celui de global.json.
  2. La CI ne couvrait pas les pushes directs sur main.
  3. Un fichier App.config vide restait référencé.

Le run a épinglé le SDK du scan, ajouté le déclencheur de push et retiré la référence vide. La nouvelle revue rapportait zéro constat dans les catégories Critical, High, Medium et Low, avec les 20 tests toujours réussis. Ce résultat appartient à ce run et à son périmètre de vérification.

Décision finale

Un verdict Go ne publie rien tout seul. L'utilisateur doit choisir entre préparer une release candidate, demander des modifications ou arrêter. Le parcours documenté attendait encore cette validation finale.

Le bilan historique indiquait 8 tours, 11 délégations et environ 0,72 USD, soit 72 crédits IA estimés. Ce n'est ni une mesure de facturation ni une prévision pour votre code. Les deux interventions intermédiaires concernaient la réaffectation du chercheur et l'approbation du risque.

En cas de blocage

  • Outillage absent : consignez le blocage et demandez une décision sur la suite.
  • SDK indisponible : distinguez l'analyse achevée des tests non exécutés.
  • Revue propre dès le premier passage : présentez les preuves réelles sans inventer des erreurs corrigées.
  • Demande de livraison immédiate : les validations et conditions de fusion restent applicables.
