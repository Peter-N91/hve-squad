Guide contributeur

Contribuer

Proposez un changement ciblé, accompagnez-le de preuves et faites-le relire avant publication.

De la proposition au package

Le guide de contribution du dépôt (anglais) reste la référence. Le package ne lit pas les environnements consommateurs : une modification entre dans la distribution par une pull request, pas par une remontée automatique des fichiers locaux.

  1. Créez un fork et une branche pour votre changement.
  2. Modifiez les sources concernées et ajoutez les tests adaptés.
  3. Ajoutez un fragment avec apm run change.
  4. Ouvrez une PR vers la branche par défaut avec le périmètre et les vérifications réalisées.
  5. Traitez les remarques de revue. Un mainteneur décide de la fusion et de la publication.

Enregistrer le changement

Ne modifiez pas CHANGELOG.md ni la version dans apm.yml : ce sont des sorties de publication. Ajoutez un fichier distinct dans .changes/unreleased/ pour éviter les conflits entre PR.

apm run change

Le script demande le type, le niveau de version, un titre pour le nom de fichier et le texte destiné aux notes de publication. Les types admis sont Added, Changed, Deprecated, Removed, Fixed et Security.

NiveauQuand le proposer
patchCorrection ou extension d'un concept existant, y compris un agent ou un rôle supplémentaire.
minorNouveau concept ou changement important de la manière d'utiliser le package.
majorChangement qui impose une adaptation au consommateur.
---
bump: patch
type: Fixed
---

- **Corrected a missing role mapping.** Updated the roster to use the deployed agent.

Les valeurs techniques et les notes de publication du dépôt restent en anglais. Commencez les entrées par - , nommez le problème en gras, décrivez le changement et citez les chemins utiles. Un fragment correspond à une idée ; le mainteneur peut corriger le niveau avant fusion.

Préversion et correctif isolé

Une fusion ne publie pas une version stable. Les fragments attendent la décision du mainteneur. La préversion glissante permet de tester le contenu déjà fusionné ; son tag exact figure sur Releases. Elle change à chaque fusion : épinglez une version publiée pour un usage durable.

Une publication livre un commit entier, pas une sélection de fragments. Si main contient du travail qui ne doit pas partir, un mainteneur prépare une branche de correctif depuis le dernier tag et y applique uniquement les changements nécessaires. Release Prep cible cette branche, puis le résultat est réintégré selon la procédure du dépôt.

Améliorer la documentation

Les pages correspondantes de docs/ et docs/fr/ doivent évoluer ensemble. Conservez les noms de commandes et de paramètres, vérifiez les liens et les ancres, puis contrôlez le rendu mobile. Les styles et interactions sont partagés ; aucune compilation frontend n'est nécessaire.

Partager un apprentissage

La mémoire active des agents reste locale. /squad-learn prépare une proposition nettoyée pour revue humaine ; elle n'est jamais promue automatiquement. Un apprentissage général peut rejoindre le package public, un apprentissage propre à une organisation doit rester dans son dépôt privé.

  • Retirez secrets, jetons, identifiants et chaînes de connexion.
  • Retirez les noms de clients, d'organisations et de personnes.
  • Retirez les chemins absolus et URL internes.
  • Généralisez les détails propres au projet sans perdre la leçon vérifiable.
  • Confirmez que le destinataire est autorisé à recevoir le contenu.

Les apprentissages partagés résident dans squad-src/.github/skills/squad/learnings/shared-learnings.md. Le modèle de partage (anglais) décrit les voies publique et privée. La revue humaine protège contre les fuites, les règles erronées et l'altération de la mémoire.
