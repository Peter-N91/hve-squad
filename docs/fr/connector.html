Guide d'intégration

Squad Connector

Conservez vos propres agents, compétences et limites d'exécution. Enregistrez un manifeste de capacité et déléguez les tâches bornées à votre coordinateur externe via le connecteur Squad Connector, sans rien migrer dans ce package.

Parcours consommateur : votre chercheur et votre coordinateur d'implémentation

Votre squad existe déjà. Votre organisation possède un agent de recherche avec ses propres compétences et un coordinateur d'implémentation qui pilote vos agents de code et de validation. Cet exemple en fait les endpoints automatiques des rôles researcher et developer, puis ajoute un spécialiste .NET ou GCP sans remplacer un autre membre.

Utilisez un package Squad compatible avec le contrat connecteur 1.1 et votre hôte/adaptateur d'agents existant. L'adaptateur exécute vos agents et échange les fichiers de demande/résultat avec HVE. Coordinator, Federation Coordinator, Scribe et council restent inchangés. Votre coordinateur d'implémentation sert le rôle développeur, pas le rôle Coordinator HVE.

Étape 1 : Créer les dossiers dans votre dépôt

Créez le dossier des manifestes et les boîtes de dépôt ci-dessous. Les fichiers d'agents sont des modèles facultatifs pour votre propre hôte ; réutilisez vos agents et compétences existants. HVE/Scribe gère les fichiers d'état de squad figurant en bas de l'arborescence.

Copiez les manifestes complets depuis Copier les modèles dans les deux fichiers ci-dessous. Un manifeste décrit les capacités et le transport ; l'inscription de l'étape 3 détermine le rôle de squad remplacé.

Dans la configuration de confiance de votre adaptateur, associez le premier identifiant à votre chercheur et le second à votre coordinateur d'implémentation. Les noms d'exemple sont Consumer Research Agent et Consumer Implementation Orchestrator. Ce dernier délègue à ses propres agents d'implémentation et de validation, qui conservent leurs compétences.

Cette association dépend de l'hôte ; HVE ne lit aucun fichier d'adaptateur inventé et ne déduit pas un agent de son nom de fichier. Le tableau roles du manifeste est une liste d'autorisation des rôles pouvant être liés à ce connecteur, et non un remplacement automatique de tous les rôles listés. Vos fichiers .agent.md et compétences peuvent résider dans le dépôt ou dans un dossier externe partagé : votre script adaptateur surveille .connector-drops/, associe connectorId à votre agent ou workflow, l'exécute sur les sources citées dans request.task (les textes génériques sans citations étant rejetés) et écrit l'enveloppe de résultat. N'ajoutez pas de champ d'exécution de commande ou de fichier d'agent au manifeste. Adaptez l'adresse de contact, les identifiants et les chemins de façon cohérente.

Étape 4 : Utiliser normalement votre squad

Lancer l'autopilote avec les défauts enregistrés
/squad mode=autopilot Implement the approved validation change and its regression tests. Do not deploy or push.

Aucun paramètre execution= n'est requis. La recherche utilise votre chercheur ; la planification reste avec le lead ; l'implémentation utilise votre workflow ; la revue finale et les gates council/risque HVE restent applicables. Les autres rôles de travail utilisent le même mécanisme.

Votre adaptateur doit fonctionner pour traiter les demandes. Avec le dépôt de fichiers, un résultat non prêt laisse l'étape sur awaiting, sans remplacement silencieux par l'agent interne. Votre automatisation peut reprendre le flux. Pour une remise manuelle, continuez la même tâche :

Reprendre un échange en attente, si nécessaire
/squad mode=autopilot Continue the current run. Check the pending connector result using its existing taskId and binding; do not create a new task.

Le connecteur ne fournit ni runner externe ni service de réveil automatique entre processus.

Étape 6 : Retrouver les sorties et l'historique

Les boîtes contiennent les demandes/résultats, pas l'emplacement final des rapports. La recherche utilise le Deliverable Root actif du chercheur ; le workflow, ses sorties déclarées ; les spécialistes, leurs racines confirmées. Le code et les tests restent dans le worktree autorisé. Le Scribe conserve les références et les identités de membre/liaison dans le squadRoot propriétaire, dont history/Squad Connector.md (où chaque rôle connecté est distingué par son Member Name unique et dispose de sa propre ligne dans consumption.md).

Le travail externe reste external, unverified ; ses coûts ne sont pas mesurés par le shim. Les liaisons restent attachées à cette squad après promotion en fédération. La référence sur les sorties et la fédération détaille le rebasage et les échanges en cours.

Qu'est-ce que le Squad Connector ?

Le Squad Connector est un contrat d'intégration basé sur fichier qui vous permet de ramener votre propre coordinateur (ou agent unique) dans la méthodologie HVE Squad. Vous enregistrez un manifeste de capacité unique décrivant ce que votre coordinateur peut faire, où il réside sur le disque et quels rôles de l'équipe peuvent lui déléguer du travail. Lorsqu'un rôle délégué a besoin de travail externe, le shim Squad Connector écrit une enveloppe de demande de délégation au chemin de dépôt de votre manifeste. Votre propre coordinateur (s'exécutant entièrement en dehors de ce package) la lit, effectue le travail et écrit une enveloppe de résultat avec le livrable. Le shim valide et signale le résultat, exactement comme il signale le résultat de tout autre rôle.

Vous conservez vos propres agents, compétences et limites d'exécution. Rien dans ce package n'exécute ou n'installe votre code coordinateur. Aucune migration de vos outils, aucune bifurcation de votre méthodologie. Le connecteur est un shim qui transmet le travail à travers une limite et ramène les résultats — rien de plus.

Aucun blocage, aucun MCP, aucun transport en direct. Le connecteur implémente le mode 2 : dépôt de fichier avec boucle humaine. Le shim écrit la demande de délégation et revient immédiatement ; votre coordinateur s'exécute selon votre propre calendrier (par observateur de fichiers, tâche cron, main humaine ou ce que vous préférez), et le shim récupère le résultat lors d'une délégation ultérieure. C'est le seul mode de transport pris en charge aujourd'hui.

Adaptation architecturale : Distribution externe

Les modes de rôle du connecteur sont pilotés par le roster. Pendant l'inscription/la construction/le rafraîchissement, les consommateurs ajoutent des entrées dans Connector Bindings et choisissent si chaque liaison remplace une surface d'exécution existante ou ajoute un nouveau membre d'équipe soutenu par connecteur. Le point de terminaison derrière la liaison peut être un agent externe unique ou un orchestrateur externe.

Le mode remplacement conserve l'original interne. Au moment de la demande, l'exécution peut choisir original, un connector:<binding-id> nommé, ou both quand les sorties sont sans collision. La clarification interactive intervient après la classification ordinaire du rôle si un doute reste. En mode non assisté/autopiloté, toute ambiguïté restante est traitée en échec fermé : arrêt et escalade, jamais de choix implicite.

Plusieurs membres connecteur additifs sont pris en charge. Exemple : une squad Azure peut ajouter un évaluateur d'architecture gcp soutenu par connecteur et aligné sur azure-architect. Cet alignement donne uniquement une compatibilité de routage et de livrables. Il ne donne pas de capacité Azure par implication, et il ne donne aucune appartenance aux lentilles du council.

La coquille de gouvernance et le council restent internes. Même quand une liaison utilise votre orchestrateur externe pour un rôle de travail, le Squad Coordinator HVE reste la coquille de gouvernance. Les orchestrateurs externes ne peuvent pas détenir les gates, les verdicts de council, les approbations, les écritures d'état de squad, ni l'autorité Scribe. Le council reste canonique/interne et les rôles connecteur ne l'étendent ni ne le remplacent.

Le modèle des places : vos agents, la gouvernance HVE

HVE pilote la méthode ; vos agents réalisent le travail délimité. Un rôle est une place : gardez l'agent HVE, choisissez votre agent avec ses compétences, ou placez votre workflow complet derrière ce rôle. Votre workflow d'implémentation ne remplace pas le cycle Recherche → Planification → Implémentation → Revue de la squad.

PlaceChoix du consommateurResponsabilité HVE conservée
researcherVotre chercheur et vos compétences de rechercheOrdre des étapes et contrôle des livrables
developerVotre implémenteur ou votre orchestrateur recherche/code/validationPrérequis du plan, council si nécessaire, et revue finale
Spécialiste supplémentaireGCP, pratiques .NET, qualité des données ou autre capacité déclaréeRoutage, confirmation, preuves et composition inchangée du council
Coordinateur et ScribeGouvernance et persistance internesGates, admission, approbations, décisions, historique et synthèse

La revue interne de votre endpoint apporte des preuves, pas un verdict de council ni une autorisation de livraison. Le Coordinator HVE, le Federation Coordinator et le Scribe ne peuvent être ni connectés ni remplacés. Votre orchestrateur prend un rôle de travail tel que developer, jamais la place du coordinateur HVE.

Référence des choix d'exécution

Demandez au Squad Coordinator d'inscrire ou de rafraîchir un connecteur en donnant le chemin du manifeste. Il pose les questions manquantes une à une, valide une configuration manuelle complète sans répéter les décisions déjà fournies, puis demande confirmation avant toute écriture du Scribe. Choisissez replace avec le défaut connector pour utiliser votre endpoint par défaut, ou ask pour en faire une alternative choisie à chaque demande. Choisissez add pour un membre supplémentaire. Ne placez pas les identifiants de connecteur dans Alternate Agents.

Configurez une fois, puis lancez l'autopilote sans paramètre d'exécution. Les défauts du parcours sélectionnent votre chercheur et votre workflow d'implémentation. La planification, la revue, l'architecture, la rédaction et les autres rôles de travail utilisent le même mécanisme. Un rôle sans liaison reste interne ; les délégations de council restent toujours internes.

RôleLiaisonDefault Execution
researcherresearch-orgconnector
developerimplementation-orgask (alternative à agent unique)
developerdeveloper-delivery-orchestratorconnector

Les capacités additives ne se limitent pas à GCP. Chacune nécessite un rôle autorisé par le manifeste, un nom de membre unique, une liaison, une route et une racine explicites, et un alignement sur une classe existante. Par exemple, gcp s'aligne sur azure-architect, tandis que dotnet-practices et data-quality s'alignent sur tester. Votre endpoint fournit les compétences réelles ; l'alignement ne les crée pas. Coordinateurs, Scribe et council restent réservés. 

/squad mode=autopilot Implement the approved validation change and its regression tests. Do not deploy or push.
/squad Assess GCP architecture
/squad Assess dotnet practices
/squad Assess dataset quality

Pour choisir un agent d'implémentation unique, confirmez un rafraîchissement mettant sa liaison sur connector et celle du workflow sur ask. La commande d'autopilote reste identique. Il faut exactement un défaut applicable différent de ask. execution= reste une surcharge facultative d'un rôle de travail.

Commencez par le parcours consommateur de cette page. Le guide consommateur en est la version Markdown, avec les mêmes dossiers, décisions d'inscription et destinations des sorties. L'exemple d'équipe propose une variante plus large, avec un implémenteur unique par défaut et trois capacités supplémentaires. Ces modèles restent dans les sources ; ils ne sont ni installés ni exécutés automatiquement. Mettez à jour ou reconstruisez votre package installé pour bénéficier des changements.

La sélection automatique est distincte du transport. Votre adaptateur exécute l'endpoint externe. Le dépôt de fichiers peut laisser l'étape sur awaiting ; votre automatisation ou une reprise ultérieure vérifie la même tâche. Aucun runner externe ni service de réveil automatique n'est fourni par ce package.

Le manifeste de capacité

Vous créez un fichier JSON unique, le manifeste de capacité, qui décrit votre connecteur. L'équipe n'exécute jamais ce fichier ; elle le lit comme données pour valider et acheminer le travail.

Champ Type Requis Signification
connectorId string oui Identifiant stable de ce connecteur, utilisé pour lier chaque demande et résultat. Choisissez quelque chose comme acme-coordinator-v2.
schemaVersion string oui La version du contrat ciblée par ce manifeste. Utilisez "1.0" pour le flux hérité à rôle unique, "1.1" pour les modes de rôle.
transport string oui Le mode d'invocation. Doit être "file" (aucune autre valeur n'est prise en charge). "mcp" est réservé pour un possible futur transport ; ne l'utilisez pas.
endpointKind string 1.1 : oui
1.0 : omettre		 Ce qui se trouve derrière la limite du connecteur : "agent" ou "orchestrator".
capabilities tableau de string oui Description en prose de ce que votre coordinateur peut faire. Pas exécutable. Exemple : "Implements a bounded development task against our in-house coding standard and returns changed files."
roles tableau de string oui Quels ID de rôle de l'équipe ce connecteur peut être enregistré. Exemple : ["developer", "reviewer"]. Consultez le catalogue du roster pour les ID de rôle valides.
dropPath string oui Chemin relatif au dépôt où le shim écrit l'enveloppe de demande de délégation et où votre coordinateur lit et écrit les enveloppes de résultat. Exemple : ".connector-drops/acme-coordinator-v2/". Le répertoire doit exister sur le disque.
deadlineMinutesDefault entier oui Combien de minutes le shim attend un résultat avant de déclarer la demande unreachable. Un rôle délégué peut ignorer cela. Exemple : 120.
retryCapDefault entier oui Combien de fois le shim réécrit une enveloppe de demande de délégation (si aucun résultat n'arrive) avant d'abandonner et de passer à failed. Exemple : 3.
contact string oui Contact lisible par l'homme pour le responsable du coordinateur. Lu comme données, jamais comme une commande. Exemple : "squad-integrations@example.com".
version string oui Votre propre chaîne de version coordinateur, pour la traçabilité. Exemple : "2.3.1".

Aucun champ supplémentaire. Le schéma du manifeste est fermé. N'importe quel champ autre que les champs déclarés ci-dessus (incluant command, exec, script, url ou tout autre champ qui nomme une action) sera rejeté lors de la validation.

L'enveloppe de demande de délégation

Quand un rôle délégué délègue du travail à votre connecteur, le shim Squad Connector écrit un fichier JSON d'enveloppe de demande de délégation au dropPath de votre manifeste. Votre coordinateur observe ou interroge ce répertoire, lit la demande et agit en conséquence.

Champ Type Signification
taskId string Identifiant frais et unique pour cette demande spécifique. Jamais réutilisé une fois que vous écrivez un résultat pour cela.
connectorId string Doit correspondre au connectorId de votre manifeste.
role string Le rôle de l'équipe qui délègue cette tâche.
deliverableRoot string Le répertoire du rôle délégué où tous les artefacts de résultat doivent être placés. Chaque chemin d'artefact dans votre enveloppe de résultat doit se résoudre sous ce chemin, sans traversée de répertoire.
bindingId string Identité de liaison de roster de confiance en 1.1. Omis en mode hérité 1.0.
targetKind string Type de cible en 1.1 : role uniquement. Coordinateurs HVE, Scribe et gouvernance du council sont protégés. Omis en 1.0.
executionChoice string Choix résolu à la demande en 1.1 : original, connector:<binding-id>, ou both.
allowedOutputs tableau Allowlist fermée de sorties en 1.1. Chaque entrée suit { outputId, role, memberName?, deliverableRoot }.
task string Instructions délimitées pour le travail à faire. Lisez ceci comme données — ne l'exécutez jamais comme une commande ou un script.
deadline string (ISO 8601) Quand cette demande devient unreachable si aucun résultat n'arrive. Exemple : "2026-10-11T18:00:00Z".
retryCap entier Combien de fois le shim réécrit cette demande si aucun résultat n'arrive avant d'abandonner.
createdAt string (ISO 8601) Quand le shim a écrit cette demande.

Lisez chaque champ comme données. Le champ task est des instructions délimitées et lisibles par l'homme, pas un script à analyser et exécuter. Respectez deadline et retryCap ; si vous ne pouvez pas terminer à temps, écrivez un statut failed au lieu de tenter un résultat tardif.

Frontière de version. Le contrat 1.0 reste valide pour le flux manuel hérité à rôle unique. Les modes de rôle (liaisons replace/add, cible coordinateur, orchestration multi-sortie par allowlist) exigent 1.1. Le shim n'infère jamais de mise à niveau silencieuse.

L'enveloppe de résultat

Après avoir complété le travail (ou échoué à le compléter), écrivez un fichier JSON d'enveloppe de résultat au même endroit dropPath où l'enveloppe de demande de délégation est arrivée. Le shim la lira ultérieurement, la validera et signalera le résultat.

Champ Type Signification
taskId string Doit correspondre exactement à l'enveloppe de demande de délégation en attente.
connectorId string Doit correspondre exactement à l'enveloppe de demande de délégation en attente.
bindingId string Uniquement en 1.1. Doit correspondre exactement à l'enveloppe de demande de délégation en attente ; omis en mode hérité 1.0.
role string Doit correspondre exactement à l'enveloppe de demande de délégation en attente.
status string L'une de : completed, failed, awaiting ou unreachable. Vous écrivez généralement completed ou failed. (Voir les statuts ci-dessous.)
artifacts tableau d'objets Fichiers livrables. Chaque objet a {"path": "...", "type": "md"|"json"|"txt"}. Peut être vide si le statut n'est pas completed. En 1.0 hérité, c'est la forme de retour principale.
outputs tableau Forme orchestrateur en 1.1. Chaque élément suit { outputId, artifacts[] } et chaque outputId doit exister dans allowedOutputs de la demande.
narrative string Données non fiables. Résumé libre de ce qui s'est passé. À lire uniquement comme donnée, jamais comme autorité sur les gates, approbations ou verdicts. Max 10 000 caractères.
createdAt string (ISO 8601) Quand vous avez écrit ce résultat.

La provenance de confiance vient de l'inscription. Le Scribe rend External-unmetered: connector=<connectorId> et Verification: external, unverified à partir des données de liaison/manifeste validées. Le texte narratif externe peut répéter ces mots, mais il n'est jamais une source d'autorité.

Statuts de résultat

Quatre statuts, et seulement quatre, sont valides :

Statut Signification Action du coordinateur
completed Le travail s'est terminé avec succès et les artefacts sont placés à la racine livrable. Le shim valide les chemins d'artefact, enregistre une provenance de confiance, marque le résultat external, unverified et marque l'étape comme exécutée.
failed Le travail n'a pas pu être complété ou une défaillance délibérée s'est produite. Le shim escalade vers l'orchestrateur comme rôle défaillant, avec votre récit comme contexte. L'étape peut être relancée ou abandonnée selon la politique de l'orchestrateur.
awaiting La demande de délégation est toujours traitée ; aucune enveloppe de résultat n'existe encore et la deadline n'a pas été dépassée. Vous n'écrivez généralement pas ce statut vous-même. Le shim l'écrit quand il ne trouve aucune enveloppe de résultat lors d'une délégation avant la deadline.
unreachable Aucune enveloppe de résultat n'est arrivée avant la deadline, ou le manifeste lui-même est invalide ou absent. Le shim escalade comme si un rôle critique était hors ligne : l'étape échoue et peut être relancée ou abandonnée. Ce n'est pas un timeout léger ; c'est traité comme une ressource manquante.

Mode 2 : flux de dépôt de fichier avec boucle humaine

Le connecteur implémente exactement un mode d'invocation :

  1. La classification de rôle se résout, puis le choix d'exécution se résout. Le coordinateur classe d'abord le rôle/membre en interne, puis applique les liaisons de connecteur et le choix à la demande (original, connecteur nommé ou both sans collision). La clarification interactive intervient seulement si une ambiguïté subsiste ; en mode non assisté, cette ambiguïté provoque arrêt et escalade.
  2. Le shim écrit l'enveloppe de demande de délégation. Le shim Squad Connector écrit un fichier JSON au dropPath de votre manifeste. La demande contient le travail borné, les contraintes temporelles, et en 1.1 les allowlists fiables de liaison/sortie. Le shim revient immédiatement avec le statut awaiting — il ne bloque pas en attente de votre réponse.
  3. Votre coordinateur observe/interroge. Votre coordinateur (s'exécutant entièrement en dehors de ce package) observe le dropPath pour les nouvelles enveloppes de demande de délégation par les moyens que vous choisissez — observateur de fichiers, tâche cron, script déclenché manuellement, etc. Il n'y a pas de mécanisme prescrit.
  4. Le coordinateur effectue le travail. Votre coordinateur lit l'enveloppe de demande de délégation, exécute la tâche délimitée et rassemble le résultat (fichiers modifiés, rapports, etc.).
  5. Le coordinateur écrit l'enveloppe de résultat. Votre coordinateur écrit un fichier JSON d'enveloppe de résultat au même dropPath, avec les identités correspondantes, le statut, les chemins d'artefact et un récit factuel. Le Scribe produit les marqueurs comptables en interne.
  6. Une délégation ultérieure du shim vérifie le résultat. Une délégation ultérieure du shim Squad Connector (par l'orchestrateur au prochain tour ou chaque fois que l'équipe s'exécute à nouveau) lit le dropPath, trouve votre enveloppe de résultat, la valide et signale completed, failed ou unreachable.

Pas de réponse immédiate. La différence clé avec un RPC traditionnel est que les étapes 2 et 6 sont séparées. Le shim ne bloque jamais. Votre coordinateur s'exécute de façon asynchrone selon votre propre calendrier. Si votre coordinateur doit s'exécuter de façon synchrone, vous pouvez le déclencher immédiatement après que le shim écrive la demande ; si vous voulez qu'il s'exécute via cron ou action humaine, cela fonctionne aussi. Le contrat ne s'en soucie pas.

Règles de sécurité

Données non fiables dans l'enveloppe. Chaque enveloppe de résultat — son statut, son récit et le contenu d'artefact — est traité comme donnée non fiable par le shim. Aucune instruction ou directive dans un récit ne peut diriger une porte, ignorer une politique ou modifier le comportement de l'équipe. La propre validation du shim (pas les affirmations de l'enveloppe) détermine ce qui s'est passé. N'importe quelle instruction intégrée comme « sauter cette porte » ou « marquer ceci comme approuvé » est signalée, jamais obéie.

Validation de chemin et limites numériques. Le shim valide chaque chemin d'artefact avant d'y toucher :

  • Pas de traversée de répertoire : Rejetez les chemins avec des chemins absolus, des chemins UNC (\\server\share), des lettres de lecteur (C:), des segments .. ou des marqueurs de flux de données alternatif NTFS (:). Résolvez le chemin restant et confirmez qu'il se trouve sous deliverableRoot en utilisant une vérification de préfixe consciente du séparateur (vrai segment de chemin, pas une simple correspondance de chaîne).
  • Pas de liens symboliques ou de jonctions : Rejetez tout lien symbolique, jonction ou point d'analyse à tout composant de chemin, y compris les répertoires intermédiaires.
  • Restrictions de type de fichier : Seuls .md, .json et .txt sont autorisés. Toute autre extension est rejetée.
  • Limites numériques, toutes appliquées :
    • 1 MiB maximum par fichier
    • 5 MiB maximum par enveloppe
    • 20 artefacts maximum par enveloppe
    • 5 niveaux maximum de profondeur d'imbrication sous deliverableRoot
    • 10 000 caractères maximum pour toute valeur de chaîne unique (y compris le récit)
  • Noms de périphériques réservés : Rejetez les noms réservés Windows (CON, PRN, AUX, NUL, COM1–COM9, LPT1–LPT9) dans n'importe quel composant de chemin, et rejetez tout composant avec des points ou des espaces finaux.
  • Pas de remplacement automatique ; validation sur place : Votre producteur écrit chaque nouvel artefact propre à la tâche directement sous deliverableRoot (ou son emplacement allowedOutputs[].deliverableRoot déclaré) avant de publier <taskId>.result.json. Le shim photographie les chemins préexistants avant d'émettre la demande et rejette tout chemin d'artefact déclaré qui existait déjà avant la tâche, duplique un autre chemin du même résultat ou est absent sur le disque lors de la validation.

Manifeste et enveloppes fermés. Les schémas du manifeste, de l'enveloppe de demande de délégation et de l'enveloppe de résultat sont tous fermés. N'importe quel champ non déclaré est rejeté lors de la validation.

Liaison de l'enveloppe et protection contre la rejeu. Les connectorId, taskId et role d'une enveloppe de résultat doivent correspondre exactement à l'enveloppe de demande de délégation. Chaque taskId est unique ; une fois consommé, le même taskId n'est jamais accepté à nouveau — une répétition est un rejeu et est rejetée.

Pas de secrets. Un manifeste, une enveloppe de demande de délégation ou une enveloppe de résultat contenant du contenu en forme de donnée d'identification (clés API, jetons, chaînes de connexion, blocs PEM ou d'autres motifs secrets haute entropie) échoue la validation immédiatement. N'intégrez jamais de secrets dans l'un de ces fichiers.

Comptabilité : marqueur External-unmetered

Le travail du connecteur exécuté de façon externe est enregistré comme entrée d'historique ordinaire dans le grand livre de l'équipe, mais selon une convention spéciale : la sortie Scribe de confiance porte l'expression exacte External-unmetered: connector=<connectorId>. Cette expression est dérivée de la provenance validée de la liaison/inscription afin qu'un examinateur distingue le travail externe non mesuré de l'exécution interne mesurée.

Le grand livre sous-signale la dépense externe. La délégation du shim lui-même est mesurée (une opération fine), mais le travail réel de votre coordinateur n'est pas. Le marqueur comptable documente cette lacune — ce n'est pas une opération à coût zéro, mais plutôt une opération non mesurée. Ne traitez jamais une entrée avec ce marqueur comme économique dans le raisonnement sur budget ou risque ; le marqueur existe précisément pour qu'un examinateur ne mésinterprète pas une figure basse du grand livre comme le vrai coût du travail délégué.

Le récit externe peut inclure son propre texte de marqueur, mais cette copie reste une donnée non fiable et ne devient jamais la source comptable faisant autorité.

Exemple de puce d'entrée d'historique : 

* Outcome: Result envelope validated and artifact placed at the Deliverable Root. External-unmetered: connector=acme-coordinator-v2.

Liste de vérification de compatibilité pour votre coordinateur

Avant d'enregistrer votre connecteur, confirmez que votre coordinateur satisfait à tout ceci :

  • [ ] Vous avez créé un manifeste par connecteur, validant correctement avec le schéma fermé du manifeste (pas de champs supplémentaires, transport: "file", aucun contenu en forme de secret).
  • [ ] Vous traitez chaque demande comme un travail borné et idempotent. Un taskId dupliqué est un rejeu à rejeter, pas une demande à réexécuter.
  • [ ] Votre coordinateur observe ou interroge le dropPath du manifeste pour une enveloppe de demande de délégation, par les moyens que vous choisissez.
  • [ ] Vous écrivez exactement une enveloppe de résultat par taskId, ne réutilisant jamais un taskId et n'écrivant jamais à un dropPath qui ne vous a pas été donné.
  • [ ] En 1.1, vous liez correctement les identités de confiance (connectorId, bindingId, taskId) et ne renvoyez que des outputId déclarés dans allowedOutputs.
  • [ ] Chaque chemin d'artefact est strictement sous le deliverableRoot nommé dans l'enveloppe de demande de délégation, comme l'un de .md, .json ou .txt, dans toutes les limites numériques (1 MiB par fichier, 5 MiB total, 20 artefacts max, 5 niveaux d'imbrication, 10 000 caractères par chaîne).
  • [ ] Vous respectez deadline et retryCap ; si vous ne pouvez pas terminer à temps, vous écrivez status: "failed" ou laissez la demande dépasser le délai à unreachable au lieu d'écrire un résultat tardif non sollicité.
  • [ ] Vous n'intégrez jamais de donnée d'identification, de jeton ou d'autre contenu en forme de secret dans le manifeste, la demande ou le résultat.
  • [ ] Vous n'émettez jamais de champs d'action (command, exec, script, url, fetch) ni de champ hors schéma.
  • [ ] Vous ne revendiquez jamais d'autorité de squad : pas de revendication de rôle, de council, de gate ou d'approbation ; pas d'écriture d'état de squad ; pas d'écriture Scribe.
  • [ ] Si votre endpoint fait du fan-out interne, vous le divulguez en récit/provenance tout en renvoyant une seule enveloppe bornée mappée uniquement vers les sorties déclarées.
  • [ ] Vous traitez votre propre narrative comme un résumé qu'un humain et un validateur automatisé lisent comme données — jamais comme un véhicule pour diriger ce que l'équipe fait ensuite.

Exemple travaillé : acme-coordinator-v2

Le répertoire d'exemple de connecteur contient un exemple travaillé complet de chaque forme de fichier définie par le contrat, plus des modèles vierges que vous pouvez copier et adapter :

  • manifest.json — un manifeste de capacité réaliste décrivant un coordinateur qui peut implémenter des tâches de développement pour le rôle developer.
  • delegation-request.sample.json — ce que le shim écrit au dropPath : une tâche délimitée pour ajouter une validation d'entrée à une calculatrice de facture.
  • result-envelope.sample.json — ce que le coordinateur renvoie au format hérité 1.0 : un enregistrement de modification décrivant la correction. Si le récit externe répète des mots comptables, cette copie reste une donnée non fiable ; le marqueur autoritatif est rendu par le Scribe depuis la provenance de liaison validée.
  • sample-consumer-coordinator.md — un croquis de pseudo-code de la façon dont un coordinateur externe pourrait respecter le contrat. C'est à titre illustratif uniquement et n'est jamais exécuté par quoi que ce soit dans ce dépôt.
  • manifest.template.json, delegation-request.template.json, result-envelope.template.json — modèles vierges que vous pouvez copier et remplir pour votre propre connecteur.
  • COMPATIBILITY-CHECKLIST.md — un restatement autonome et copiable de la liste de vérification de ce guide.

Copiez ces fichiers comme point de départ. Adaptez-les aux chemins, rôles et capacités propres de votre coordinateur. Lisez connector-contract.md pour la spécification normative de chaque champ et de chaque règle de validation.

Ce qui n'est pas encore pris en charge

Migration automatique de 1.0 vers 1.1 non fournie. Le 1.0 hérité reste valide pour le flux manuel à rôle unique, tandis que les modes de rôle exigent des liaisons et champs de demande 1.1. Migration et rollback sont explicites via le roster : routez vers execution=original, ou supprimez les liaisons et retirez/réaffectez les membres et routes concernés lors d'un rafraîchissement confirmé. Aucune montée de version ni rétrogradation silencieuse.

Transport MCP (réservé, pas encore construit). Le schéma du manifeste réserve une valeur transport: "mcp" comme espace réservé pour un possible futur mode de transport synchrone. Ce n'est pas implémenté aujourd'hui. Le seul mode de transport qui existe est transport: "file" (mode 2, dépôt de fichier avec boucle humaine). Un manifeste décrivant "mcp" échouera la validation. Le construire nécessite un nouveau plan gardé par la porte d'action impactful et une passe de conseil fraîche.

Agent/compétence Squad Connector Builder (T2, différé). Cette version expédie le contrat de connecteur et les modèles uniquement. Un agent ou une compétence Squad Connector Builder dédié, qui pourrait vous aider à créer un manifeste compatible et vous guider étape par étape dans l'intégration, est prévu comme suivi après observation de la façon dont les équipes utilisent l'approche basée sur modèle. Si vous êtes bloqué en créant un manifeste ou un coordinateur, consultez la page Dépannage ou contactez les responsables.
