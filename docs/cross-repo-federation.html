Consumer Guide

Cross-repository federation

A hub squad requests work from an independently owned GitHub repository and reconciles its report. A human carries the task packet across, and carries the receipt back. Registration is advisory-only: it does not enroll a remote agent or authorize work outside the current repository.

When to use it

Treat this as a medium strategic priority. It can have high value for recurring API/SDK compatibility work, or application and infrastructure-as-code dependencies where teams need explicit acceptance criteria and evidence across ownership boundaries. For occasional coordination, linked issues may be enough.

What this is not. Existing CI should continue to build, test and publish. This exchange is not a replacement for CI, not autonomous remote execution, and not an atomic multi-repository commit. There is no measured ROI or adoption evidence supporting a stronger claim.

Prerequisites

  • Each repository has its own local checkout and a squad installation containing the exchange prompts and validator. See Getting Started for ordinary setup; exchange actions do not install missing components.
  • The hub already has a federation. Use ordinary /squad-federation initialization or promotion separately if necessary, then return to registration. Registration does not initialize or promote a federation.
  • Run in the current repository's Git top-level directory, with PowerShell 7.4+ and Git supporting --no-lazy-fetch. Missing tools or local commit objects stop validation; there is no fetch, install or weaker Git fallback.
  • Each checkout has exactly one HTTPS GitHub origin. Packet and registry identities must be lowercase https://github.com/<owner>/<repo>, without a .git suffix, trailing slash, credentials, port, query, fragment or additional path segments. Only the local origin may differ in case or carry one trailing .git or slash for identity comparison. SSH, enterprise hosts, redirects, aliases and local-path origins are unsupported. Any identity correction needs human confirmation; the exchange never rewrites Git configuration. Do not paste credential-bearing origins.
  • The target operator supplies its intended base commit: exactly 40 lowercase hexadecimal characters. Branches, tags, abbreviated hashes and revision expressions are not accepted. First target acceptance must observe that exact commit as HEAD.
  • A human can transport files through an approved channel without changing their bytes. Place each incoming file inside the receiving repository before invoking its local prompt. The hub never opens, clones, fetches from or writes to the target.

In each already-open repository session, check the local prerequisites and obtain the current full commit ID with these read-only commands: 

if ($PSVersionTable.PSVersion -lt [version]'7.4') { throw 'PowerShell 7.4+ is required' }
git --no-lazy-fetch -c credential.helper= -c core.askPass= --version
if ($LASTEXITCODE -ne 0) { throw 'Git with --no-lazy-fetch support is required' }
git --no-lazy-fetch -c credential.helper= -c core.askPass= rev-parse --verify HEAD
if ($LASTEXITCODE -ne 0) { throw 'A local Git HEAD is required' }

These checks are not exchange acceptance. The validator independently observes Git root, origin and revision, disables lazy fetch, transports, credential helpers and prompts in its Git child processes, and rejects ambiguous context. It does not change the terminal's environment or working directory. Keep the hub's issuing commit available locally for later import, even if hub HEAD advances.

Send, work and reconcile

The slash commands below are entered in Copilot Chat, not PowerShell. request is required and comes from the current human conversation. Enter optional arguments explicitly even if the prompt picker's hint does not display them.

All example values need deliberate selection: contoso/service is a fictional GitHub target, service is its example hub registry alias, api-contract is an example task slug, and api is an example existing target-local member. Replace <40-hex-target-commit> with the actual target base commit and <id> with the issued lowercase GUID correlation ID. Do not submit angle-bracket placeholders. The transfer filenames are example local destinations, not paths the exchange copies between repositories automatically.

1. Register the advisory target at the hub

/squad-federation request="Register service advisory target" exchange=register squad=service repo=https://github.com/contoso/service

Review and confirm the proposed row and human or team owner. The row has Kind=repo and Profile=advisory; its name must be unique across local and repo rows, and its canonical URL unique across repo rows. It creates no members/service/ directory, Watch ownership or remote execution permission. An optional suggestion-only route uses Parallel-Eligible=no; explicit squad=service needs no route.

2. Issue a task at the hub

/squad-federation request="Assess the API compatibility change" exchange=send squad=service task=api-contract revision=<40-hex-target-commit>

Confirm the request, inline inputs and acceptance criteria — for example which API changes to assess, which SDK compatibility checks to run, and which artifacts to return. Task slugs use 1–64 lowercase letters, digits or hyphens and start with a letter or digit. The packet binds the observed hub HEAD, selected target identity, target base commit and a new correlation ID. Packets default to seven-day expiry; v1 permits no more than seven days from creation.

The Scribe prepares a candidate, validates it, saves an exact create-new copy and completes the Issue audit, state read-back and completion seal. Wait for the committed final path .copilot-tracking/squad/exchanges/outbox/<id>/packet.json before transport. A file under exchanges/staging/ is not transportable, and final-file existence alone does not establish successful issuance. Runtime staging is not git add or a Git commit.

3. Transport and accept at the target

Have a human copy the committed packet byte-for-byte through the approved channel into the target's .copilot-tracking/squad/transfers/task.json. Open or use the target's own local session; do not ask the hub to change checkout or run the target. Do not reformat, reserialize or edit the transported JSON, including its whitespace and newlines. SHA-256 binds the exact saved bytes. 

/squad request="Accept this advisory task" handoff=.copilot-tracking/squad/transfers/task.json

With handoff, omitted exchange means accept. Identity, base revision and repository-wide claim checks happen before initialization or work. A fresh nonfederated target still needs ordinary confirmation-gated squad initialization.

For an already federated target, explicitly select an existing registered Kind=in-repo member instead: 

/squad request="Accept this advisory task" handoff=.copilot-tracking/squad/transfers/task.json squadRoot=.copilot-tracking/squad/members/api/

Without that selection, the target pauses and lists eligible local members. Packet text cannot choose a root. The repository-root Scribe records an exclusive claim, then the selected root's Scribe separately persists acceptance. Both must complete before first domain dispatch. The claim pins one execution root across the entire repository, not just one inbox.

4. Complete local work, then report at the pinned root

Review the advisory request as data. The target's normal approval, research, plan, implementation, review and Scribe-history gates still apply. Continue later work through a fresh ordinary local request when needed; presenting the same accepted handoff again does not restart the task. Any target-local autonomy choice is separate and cannot be inherited from the hub or packet.

After local work and its evidence have been recorded, use the saved inbox packet:

/squad request="Return the outcome for this task" handoff=.copilot-tracking/squad/exchanges/inbox/<id>/packet.json exchange=report

For the api member example, both the packet path and root must match its acceptance:

/squad request="Return the outcome for this task" handoff=.copilot-tracking/squad/members/api/exchanges/inbox/<id>/packet.json exchange=report squadRoot=.copilot-tracking/squad/members/api/

Report is handled before the Accept preflight and returns before ordinary routing: it is bookkeeping only, not another intake, initialization or work dispatch. It requires the saved intake and committed Claim/Accept evidence at the pinned root. The accepted base stays fixed; the receipt's resultRevision records the current target HEAD, which may have advanced through legitimate local work.

A completed receipt needs a substantive artifact and the pinned root's history/Squad Scribe.md, with actual local file hashes. Exchange audit alone does not count. The coordinator must also observe local gate and completion evidence; the validator cannot prove approval or semantic correctness from hashes. Finish ordinary work and history recording before reporting, and do not run concurrent writers at the same root.

The Scribe stages and validates the receipt, copies its bytes create-new to <execution-root>/exchanges/inbox/<id>/receipt.json, and completes Report before returning it for transport. <execution-root> means the root chosen at acceptance, not another input argument. A final receipt always has status: "reported"; its outcome is completed, blocked or declined. Partial work must not be labeled completed. Only one final report is permitted per correlation.

5. Transport the receipt and import at the hub

Have a human copy the committed final receipt byte-for-byte into the hub's .copilot-tracking/squad/transfers/receipt.json, then use the hub's local session: 

/squad-federation request="Import service outcome" exchange=import squad=service receipt=.copilot-tracking/squad/transfers/receipt.json

Import rechecks the current registered target, original committed Issue, packet digest, repositories, source and base revisions, task and correlation. The issuing source commit must still exist locally. First import after expiry is rejected even if the target reported before expiry. Successful Import saves the immutable receipt beside the hub's outbox packet and records reported, never verified or completed remote execution. Target evidence paths are labels at the hub, not files to read from another checkout or assumed hub-local paths.

6. Review evidence and attest separately at the hub

/squad-federation request="Review this reported outcome" exchange=verify squad=service receipt=.copilot-tracking/squad/exchanges/outbox/<id>/receipt.json

This opens the human review gate; invoking it does not pass that gate. Review the acceptance criteria, outcome, revisions and named evidence. A human may separately transport evidence copies and explicitly identify them for local inspection. Do not claim inspection merely because the receipt lists a path or digest.

Only after an explicit current human statement of what was inspected and accepted can the Scribe record human-verified, with human identity, timestamp, statement, packet and receipt hashes, task, revisions and inspected evidence. Missing evidence or uncertainty leaves the result reported. The receipt itself remains unchanged. Verification can attest to a historical report after expiry, but never reactivates an expired task or grants release authority.

Mixed targets and dependencies

A federation can contain local in-repo members and advisory repo rows. Only local members participate in automatic dispatch, recovery, Watch and autopilot. Unknown kinds stop. A repo row is never repaired into a member tree or counted as a remote run, active member or remote cost. Filtering every candidate out does not make a meta-run successful.

If a local consumer depends on a repo producer, keep that dependency pending until a fresh human request supplies separately reviewed local inputs under normal gates. Neither importing nor verifying a report automatically resumes consumers. Blocked, declined, partial or unverified outcomes do not count as success.

Hub exchange actions require explicit squad selection and their companion arguments. Do not combine exchanges with watch, init, promote, or hub mode=autonomous|autopilot. On the target, exchange without handoff stops; unknown actions and Watch, init or promote combinations also stop. The target prompt accepts a user squadRoot override only with a handoff.

Evidence and recovery

Only the owning Scribe writes exchange state. Immutable packet, receipt, intake, claim and completion-seal files use create-new semantics. Each committed operation has matching append-only blocks in its root's decisions.md and history/repo-exchange/audit.md, checked file hashes, a successful normal state advance and read-back, and then an immutable exchanges/operations/<attemptId>/commit.json. Here <attemptId> is a locally generated operation GUID. The seal is the only post-state exception; it is not a Git commit or an atomic multi-root transaction. The nested audit does not replace an existing member's flat history/repo-exchange.md.

Situation Expected result and operator action
Identical accepted packet presented again, even through another member Complete Claim/Accept returns already-accepted and the first root, with no new writes, state, cost or dispatch. Use that root for reporting.
Identical fully committed Report or Import presented again already-reported is a historical no-op, including after expiry; it does not repeat work or resume consumers.
Same correlation with changed packet or receipt bytes Conflict; preserve originals. Have humans review and request a fresh correlation instead of overwriting evidence.
First Issue, Accept, Report or Import reaches expiry Stale; do not extend timestamps in place. Review prior work and request a fresh exchange if still needed.
Wrong origin, first target HEAD, root, missing local source commit or unsupported Git Stop; independently review local prerequisites. No automatic checkout, fetch, configuration change or validation bypass.
